# Desktop remote apps

The TJN desktop distribution exposes web apps (the provider sites ChatGPT, Claude, Grok, and Gemini, and the standalone site Perplexity) as top-level surfaces next to ndev.t3code. All surfaces share one Electron `BrowserWindow`; each site gets its own `WebContentsView` attached below the T3 titlebar. Hidden views stay alive (detached, `setVisible(false)`, background throttled), so switching surfaces does not reload a site or lose its session.

Views are also created ahead of first activation for the sites in the background list. Each site is a separate Chromium renderer process for a large SPA, roughly a few hundred MB once loaded, so background loading is chosen per site in Settings → Providers → Web apps, stored as an opt-out list beside the hidden sites so a newly available site loads by default. `setAvailableSites` carries `backgroundSites`, the available sites minus the opted-out ones, and the manager preloads those other than the active one, in that order and one at a time, starting a few seconds later and waiting for each page's load (bounded by a timeout) plus a short settle before the next, so T3's own startup and first paint never compete with several heavy site loads. Whenever the background list changes, every hidden view outside it is closed to release its memory, including one still preloading. A site opened by hand outside the list keeps its view after the user leaves it until the list next changes, rather than reloading on every return. A preloaded view goes through the same creation, layout, theme, sidebar-pin, and recovery paths as any view, while its events are ignored by the shell state, which describes only the active site, so it records no history and never takes focus. It stays detached and throttled until shown, and its first show forces a repaint rather than trusting a frame produced while detached. Views are positioned when created and when shown, not on every window resize, so a window resized since the preload costs one reflow on first show.

Hidden views are also closed after going unopened for the idle limit the renderer sends with availability (`idleUnloadMinutes`: off, 1h, 4h, or 12h, default 4h). The manager records when each view was last hidden and runs one coarse sweep every few minutes, never one timer per site, and never closes the active site or one being opened. An idle-unloaded site is excluded from background preloading until it is next opened or the app restarts; otherwise the next availability or background-list change would preload it straight back and the memory would never be freed. Opening it creates a fresh view at the site's entry URL, or its persisted location when that belongs to the site.

`DesktopSurface` is `"t3code"` plus `RemoteAppSite` from `packages/contracts/src/remote-apps.ts`, whose `REMOTE_APP_SITE_INFO` gives each site a label and the provider driver that unlocks it, or `null` for a standalone site with no T3 provider: `codex` unlocks ChatGPT, `claudeAgent` Claude, `grok` Grok, and `antigravity` Gemini, while Perplexity is standalone. A provider site is available when any instance of its driver is enabled on the primary environment and the user has not hidden it; hidden sites are an opt-out list, so a newly enabled provider's site appears by default. A standalone site has nothing to follow, so it is available only once the user turns it on, an opt-in list. Both lists live in the renderer's local storage (`useRemoteAppSites.ts`), and Settings → Providers shows them on desktop. Sign-in state is deliberately not part of availability: each site signs in on its own, independently of the provider CLI. `RemoteAppSiteSync` sends the available sites through `setAvailableSites`, but only once the primary server's config has arrived, so the empty provider list at startup is not read as "everything disabled". When the active site stops being available, the renderer switches to T3 and the manager then closes the hidden view.

The surface menu never lists the active surface. On T3 it lists the available sites; on a site it lists T3 first, ruled off from the other available sites. With nothing to switch to, the titlebar shows a plain label instead of a menu trigger.

Per-site policy lives in `RemoteAppPolicy.ts` (`REMOTE_APP_SITE_DEFINITIONS`): entry URL, first-party hosts, extra sign-in hosts, and a dedicated persistent partition. ChatGPT keeps the original `persist:tjn-remote-chatgpt-v1` partition so existing sign-ins survive; the others use `persist:tjn-remote-<site>-v1`. Sites never share cookies with each other or with the host. The renderer receives shell metadata for the active site only: the active surface, a sanitized first-party location and title, navigation affordances, zoom, bounded recents, and categorized error state. A persisted location is reused only when it belongs to the site being opened. Cookies, tokens, message bodies, raw exceptions, and query/hash credentials are never placed in the shell state file.

Theme follows the app: the host sets `nativeTheme.themeSource`, so `prefers-color-scheme` in every site matches T3's light/dark choice, and each view's background is the T3 canvas color to avoid flashes while loading. Palette and sidebar theming apply only to sites with an entry in `SITE_THEMES` (`RemoteAppSiteTheme.ts`). ChatGPT gets the fuller T3 palette override; Claude, Grok, and Gemini only have their own design tokens remapped to it. Perplexity has no entry, so it keeps its own look and sidebar width and receives only the titlebar no-drag rule.

T3's sidebar width is the one source of truth for the sidebar column. The host titlebar switcher and footer sit in T3's sidebar column above and below the site view, so each themed site's own sidebar is pinned to T3's width rather than the host following each site. The inserted site CSS (`RemoteAppSiteTheme.ts`) holds width-independent rules scoped under `:root[data-t3code-sidebar-width]` that read `var(--t3code-sidebar-width)`; a small script sets that attribute and custom property on the page's root after every stylesheet insertion and navigation. Dragging T3's sidebar sends a stream of width-only theme updates, and those only rerun the script on each live view, never reinsert the stylesheet. A collapsed T3 sidebar sends a null width, which removes the pin and leaves the site at its own width. Site views share the main window's zoom, so CSS pixels line up between T3 and the sites. T3's resize rail is hidden on a remote surface because the site view covers it.

The surface menu is a small frameless child window loaded from a `data:` URL, because a renderer popover cannot appear above a `WebContentsView`. It mirrors T3's glass menus: the renderer resolves the `dropdown-glass` tint (popover color and `--glass-opacity`), border, `MenuItem` highlight, and separator colors and sends them with the theme. A transparent Electron window gets neither native rounded corners nor a native shadow, so the menu is an opaque frameless window that the platform rounds and shadows. On macOS its background is native `menu` vibrancy under the translucent tint, standing in for `backdrop-filter`; elsewhere a page cannot blur what is behind its window, so the menu paints the opaque popover color.

Navigation is HTTPS-only. A site's first-party hosts remain in its view, and top-level redirects to supported identity providers (Google, Microsoft, Apple, plus site-specific ones such as X for Grok) stay in the view so the site can finish its own sign-in. Identity-provider popups open in a controlled child window; other HTTPS destinations open in the system browser. Unsafe schemes, untrusted authentication destinations, unknown popups, media capture, and non-approved permissions are denied. Downloads pause for an explicit native save dialog and are never opened automatically.

Remote-app IPC is registered separately from preview IPC. Every command is authorized against the main T3 renderer `webContents` id, so the isolated remote view has no preload and cannot call the bridge. State writes use a same-directory temporary file followed by rename.

The distribution identity is intentionally separate from the upstream app: `ndev.t3code`, `dev.neuman.t3code`, custom user-data names, and `t3code-tjn` protocol names. Packaged maintainer builds use the local source updater rather than the GitHub Releases feed; see [local source updates](./local-source-updates.md) for how it follows upstream nightly tags and merges them into the fork.

The fork's GitHub Actions workflows are disabled. Upstream synchronization, builds, installation, and restart are local desktop operations; this design intentionally does not schedule hosted jobs, publish releases, or deploy services.

Two features read or write a page, and only through small scripts the shell runs in its own isolated world (`RemoteAppPageScripts.ts`, world `1101`), so page code cannot see or call them. Both need the site's optional `page` hooks in `REMOTE_APP_SITE_DEFINITIONS`: CSS selectors for its "generating" indicator (the Stop button) and its prompt box. The selectors are best-effort, unverified constants that break when a site redesigns; a site without hooks simply opts out. Scripts run only on a trusted first-party URL of the site, never on a sign-in page.

- **Finished-reply badge.** After each load the shell installs a MutationObserver that resolves once a reply finishes: a `generating` selector appears, then stays gone for a short settle. Checks are coalesced to one per quarter second while the DOM changes, and an idle page costs nothing, with no polling or interval. When no selector has ever matched in that document, a fallback counts mutation batches while the page is hidden after a user-initiated send (a trusted Enter or a send-button click) and fires after about 3s of quiet. It can badge early on a long mid-reply pause, misses a reply that finished before the user left, and can be fooled by unrelated hidden churn, which is why it only runs when the selectors look stale. A finished reply on a hidden site adds it to `unreadSites` in the shell state; showing the site clears it, and the list is emptied when the shell state is read at startup, since views do not survive a restart. The surface menu and titlebar switcher show a static dot, never an animation.
- **Send to T3 thread.** The view's context menu offers "Send to T3 Thread" for a text selection. The shell switches to T3 and sends `{site, text}` on a fork-only channel (`RemoteAppChannels.ts`, kept out of upstream `ipc/channels.ts`); `RemoteAppSendToThreadHost`, mounted by the titlebar switcher, appends it as a quote under the site's name to the composer draft of the last thread route the user was on, or starts a new draft in the default project.
- **Send to a site.** Finished assistant messages get a "Send to a web app" menu listing the available sites. `fillSitePrompt` switches to the site, waits for its load, and inserts the text at the end of the prompt box with `document.execCommand("insertText")`, so the site's editor sees ordinary input. It never presses Enter or clicks send. When the box can't be found, the shell puts the text on the clipboard and shows a short notice on the page itself, because the renderer's toasts sit beneath the site's view; if the page cannot show it either, the shell returns to T3 and the renderer toasts instead.

Beyond these, the surfaces do not scrape site DOM or private APIs, intercept remote network traffic, automate the remote pages, or claim passkey support for the custom bundle identity.
