# Desktop remote apps

The TJN desktop distribution exposes provider web apps (ChatGPT, Claude, Grok, Gemini) as top-level surfaces next to ndev.t3code. All surfaces share one Electron `BrowserWindow`; each site gets its own `WebContentsView` attached below the T3 titlebar. Hidden views stay alive (detached, `setVisible(false)`, background throttled), so switching surfaces does not reload a site or lose its session.

Views are also created ahead of first activation: once the renderer sends the available sites, the manager preloads the other available sites one at a time, starting a few seconds later and waiting for each page's load (bounded by a timeout) plus a short settle before the next, so T3's own startup and first paint never compete with several heavy site loads. Each site is a separate Chromium renderer process for a large SPA, roughly a few hundred MB once loaded, so the preload is a user toggle (Settings → Providers → Web apps, on by default) carried in the same `setAvailableSites` payload; turning it off stops further preloads and keeps views already created. A preloaded view goes through the same creation, layout, theme, sidebar-pin, and recovery paths as any view, while its events are ignored by the shell state, which describes only the active site, so it records no history and never takes focus. It stays detached and throttled until shown, and its first show forces a repaint rather than trusting a frame produced while detached. Views are positioned when created and when shown, not on every window resize, so a window resized since the preload costs one reflow on first show.

`DesktopSurface` is `"t3code"` plus `RemoteAppSite` from `packages/contracts/src/remote-apps.ts`, which also maps each site to the provider driver that unlocks it: `codex` to ChatGPT, `claudeAgent` to Claude, `grok` to Grok, and `antigravity` to Gemini. A site is available when any instance of that driver is enabled on the primary environment and the user has not hidden it. Sign-in state is deliberately not part of it: each site signs in on its own, independently of the provider CLI. Hidden sites are an opt-out list in the renderer's local storage (`useRemoteAppSites.ts`), so a newly enabled provider's site appears by default; Settings → Providers shows the list on desktop. `RemoteAppSiteSync` sends the available sites through `setAvailableSites`, but only once the primary server's config has arrived, so the empty provider list at startup is not read as "everything disabled". When the active site stops being available, the renderer switches to T3 and the manager then closes the hidden view.

The surface menu never lists the active surface. On T3 it lists the available sites; on a site it lists T3 first, ruled off from the other available sites. With nothing to switch to, the titlebar shows a plain label instead of a menu trigger.

Per-site policy lives in `RemoteAppPolicy.ts` (`REMOTE_APP_SITE_DEFINITIONS`): entry URL, first-party hosts, extra sign-in hosts, and a dedicated persistent partition. ChatGPT keeps the original `persist:tjn-remote-chatgpt-v1` partition so existing sign-ins survive; the others use `persist:tjn-remote-<site>-v1`. Sites never share cookies with each other or with the host. The renderer receives shell metadata for the active site only: the active surface, a sanitized first-party location and title, navigation affordances, zoom, bounded recents, and categorized error state. A persisted location is reused only when it belongs to the site being opened. Cookies, tokens, message bodies, raw exceptions, and query/hash credentials are never placed in the shell state file.

Theme follows the app: the host sets `nativeTheme.themeSource`, so `prefers-color-scheme` in every site matches T3's light/dark choice, and each view's background is the T3 canvas color to avoid flashes while loading. ChatGPT gets the fuller T3 palette override; the other sites only have their own design tokens remapped to it.

T3's sidebar width is the one source of truth for the sidebar column. The host titlebar switcher and footer sit in T3's sidebar column above and below the site view, so each site's own sidebar is pinned to T3's width rather than the host following each site. The inserted site CSS (`RemoteAppSiteTheme.ts`) holds width-independent rules scoped under `:root[data-t3code-sidebar-width]` that read `var(--t3code-sidebar-width)`; a small script sets that attribute and custom property on the page's root after every stylesheet insertion and navigation. Dragging T3's sidebar sends a stream of width-only theme updates, and those only rerun the script on each live view, never reinsert the stylesheet. A collapsed T3 sidebar sends a null width, which removes the pin and leaves the site at its own width. Site views share the main window's zoom, so CSS pixels line up between T3 and the sites. T3's resize rail is hidden on a remote surface because the site view covers it.

The surface menu is a small frameless child window loaded from a `data:` URL, because a renderer popover cannot appear above a `WebContentsView`. It mirrors T3's glass menus: the renderer resolves the `dropdown-glass` tint (popover color and `--glass-opacity`), border, `MenuItem` highlight, and separator colors and sends them with the theme. A transparent Electron window gets neither native rounded corners nor a native shadow, so the menu is an opaque frameless window that the platform rounds and shadows. On macOS its background is native `menu` vibrancy under the translucent tint, standing in for `backdrop-filter`; elsewhere a page cannot blur what is behind its window, so the menu paints the opaque popover color.

Navigation is HTTPS-only. A site's first-party hosts remain in its view, and top-level redirects to supported identity providers (Google, Microsoft, Apple, plus site-specific ones such as X for Grok) stay in the view so the site can finish its own sign-in. Identity-provider popups open in a controlled child window; other HTTPS destinations open in the system browser. Unsafe schemes, untrusted authentication destinations, unknown popups, media capture, and non-approved permissions are denied. Downloads pause for an explicit native save dialog and are never opened automatically.

Remote-app IPC is registered separately from preview IPC. Every command is authorized against the main T3 renderer `webContents` id, so the isolated remote view has no preload and cannot call the bridge. State writes use a same-directory temporary file followed by rename.

The distribution identity is intentionally separate from the upstream app: `ndev.t3code`, `dev.neuman.t3code`, custom user-data names, and `t3code-tjn` protocol names. Packaged maintainer builds use the local source updater rather than the GitHub Releases feed; see [local source updates](./local-source-updates.md) for how it follows upstream nightly tags and merges them into the fork.

The fork's GitHub Actions workflows are disabled. Upstream synchronization, builds, installation, and restart are local desktop operations; this design intentionally does not schedule hosted jobs, publish releases, or deploy services.

The surfaces do not scrape site DOM or private APIs, intercept remote network traffic, automate the remote pages, or claim passkey support for the custom bundle identity.
